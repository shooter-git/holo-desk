# Creations: music that lives in another project

A game, an app or an installation can keep its music as code and still have it edited by ear in HO[LO].
The two meet in one file per piece, a [session](session-format.md), inside the creation:

```
your-creation/
  holo.creation.json        { "format": "holo-creation", "version": 1, "name": "your-creation",
                              "title": "Your Creation", "sessions": "music/sessions",
                              "exportHelp": "how to bring a piece in", "renderHelp": "how to hear it" }
  music/sessions/
    theme.holo.json
```

1. **The creation writes the session** from its own score, with an adapter of its own. Keep it in the
   creation, or, if it's yours alone, in HO[LO]'s `local/` folder, which git ignores: a creation's
   music stays out of HO[LO]'s repository. Give each voice a track with a stable `origin.voice`.
2. **HO[LO] opens it.** It finds creations in `HOLO_CREATIONS_DIR` (each folder with a
   `holo.creation.json`). Choose *Songs → From your creations* in the studio, or run
   `holo pull your-creation theme`. Opening it again updates the same song.
3. **You edit it.** Any track whose music changes gets `origin.edited: true`.
4. **HO[LO] sends it back** (*Send to your-creation*, or `holo send`). The file is replaced atomically.
5. **The creation plays the edited tracks** in place of its own notes, and keeps everything else
   generated by its code. When it exports again, it keeps the edited tracks and brings the rest up
   to date.

HO[LO] writes only inside the `sessions` folder a creation declares, and only `<piece>.holo.json` files.

## Hearing it as the creation plays it

HO[LO]'s own playback is for editing: the same samples, but not the creation's halls, tone chains,
synthesized voices or mastering. To hear the song exactly as the creation will play it, with the edits
you've made and not yet sent, the creation can render it itself. Declare how in `holo.creation.json`:

```jsonc
"render": {
  "command": ["python3", "tools/render.py", "--preview", "{piece}"],
  "env": { "PREVIEW_OUT": "{out}", "HOLO_SESSIONS": "{sessions}" },
  "output": "{out}/music/*.wav"
}
```

`{piece}` is the piece's name, `{sessions}` a scratch folder holding the song as `<piece>.holo.json`
(what Send would write), and `{out}` a scratch folder the renderer must write into; `output` is the WAV
it leaves there (the last part may be a pattern). The renderer must read the session from `{sessions}`
and write nothing else: it is a preview, so the creation's own files stay as they are.

Renders run on the computer that has the creation, through the **creation runner**:

```bash
pnpm runner                 # keep it running; renders run one at a time
```

Then press *Hear it as …* (*Songs*, beside *Send*) or run `holo render`. The studio shows how the render
is going; when it's done the creation's WAV is on its own audio track at the top of the song, soloed,
as one undoable step (a newer render replaces it). Play to hear the creation's sound, unsolo it to hear
the studio's mix, and solo it again to compare. HO[LO]'s server never runs commands itself (it may be
in Docker, and every device on your network can reach it): only the runner does, and only the render
command each creation declares, with the piece's name checked. (The runner also starts the agent's
harness, sealed, when the agent is on: see [agent.md](agent.md).)

## Music for a new project (an experience)

HO[LO] can also be where a new project's music is written from the start: a game, an app, an
installation, anything you play with (an *experience*). Its songs are HO[LO] sessions kept in the
project, and the project builds them itself, exactly as the studio renders them (the mix, the plugins,
the stage, the halls, the finish, the loop: all of it), with a copy of HO[LO]'s engine pinned in its
repository. HO[LO] Desk doesn't have to be there: a fresh clone of the project, on any computer with
the pinned Node.js, makes the same files, sample for sample.

### Setting one up

```bash
holo init ../my-experience --title "My Experience"
```

```
my-experience/
  holo.creation.json     its name, title and songs folder, the engine it builds with (version, commit,
                         date, fingerprint, the exact Node.js) and the build's settings
  music/holo/            HO[LO]'s engine, pinned (don't edit it: holo update-engine replaces it)
    holo-music.mjs       the renderer and the build, one file (MIT)
    packs.json           the sample packs its songs play, and no others: instrument maps, where each
                         file comes from (a git commit, published downloads and how they're cut or
                         mixed, or an archive and what's decoded from it) and its sha256
    LICENSE, NOTICE.md, README.md
  music/sessions/        its songs, <piece>.holo.json, and <piece>.audio/ for a song's own recordings
  package.json           "music": "node music/holo/holo-music.mjs build"
  .gitignore             /music/build/ (the built songs are made, not written)
```

`--name`, `--sessions`, `--out` and `--format` change the defaults. Put the project in the folder the
studio reads creations from (`HOLO_CREATIONS_DIR`) so its songs show in the studio.

### Writing its songs

- `holo new "Theme" --for my-experience` makes a song that belongs to it, writes its file into
  `music/sessions/` at once and opens it in the studio; so does **New song** beside the experience in
  *Songs*. `holo send --to my-experience` gives it one of your own songs.
- Edit it in the studio, or with `holo write`, `holo fx` and the rest. **Send** (or `holo send`) writes
  the song's file: that file is the score the project builds. Edited the file itself (by hand, or an
  agent)? `holo pull my-experience theme` brings it into the studio.
- *Hear it as My Experience* (or `holo render`, with `pnpm runner` on the host) has the project render
  the open song with its own pinned engine, edits and all, onto a soloed track beside the studio's mix.

The *Songs* dialog groups songs by the experience they belong to, your own songs on their own, so moving
between several experiences' music in one studio stays clear.

### Building it

```bash
npm run music        # in the project: every song whose file changed, into music/build/
```

A song is built again only when something it is made of changed: its file, its audio files, the engine,
the Node.js that runs it or the build's settings (`music/build/.holo-build.json` keeps track; `--force`
builds them all). A song whose file is gone takes its build with it.

- **Lossless.** `"format": "wav"` (the default) is 32-bit float: exactly the engine's numbers.
  `"wav24"` is 24-bit PCM. Anything smaller for delivery (Opus, AAC…) is the project's own step, made
  from these masters. `"rate"` sets the rate (each song's own, 48 kHz when it has none) and `"tail"`
  the seconds after a song's end (a loop has its own).
- **Only the packs its songs play are pinned.** `packs.json` holds the maps of the packs the songs
  play, so a project commits a few hundred KB, not every pack HO[LO] has.
  - The engine knows every pack its commit's `packs.lock.json` pinned (its *catalog*: each pack's
    hash, kept in `holo.creation.json` and in the renderer). It plays a pack only as that map.
  - When you **Send** a song that plays a pack the project doesn't pin yet (or make a new one, or
    *Hear it as…*), the studio adds it. It fetches the pack's map from
    [HO[LO] Packs](https://github.com/shooter-git/holo-packs) at the commit the engine was pinned with,
    checks it against the catalog, then rewrites `packs.json` and `holo.creation.json` together.
  - A Send that leaves a pack unplayed lets it go. Send's note says what it pinned.
  - A pack newer than the project's engine needs `holo update-engine`, which the note says too.
  - Edited a song by hand to play another pack? Its build says the pack isn't pinned yet. Send it from
    the studio, or run `holo update-engine`, which pins exactly what the songs play.
- **Samples are fetched, never committed.** The first build fetches what its songs play:
  - VSCO 2, the VCSL and Meatbass from GitHub at the commit each pack pins;
  - the Iowa clarinet and bassoon cut from the University of Iowa's own downloads;
  - the FreePats guitar decoded from the FreePats project's own archive (a 7z of FLAC files, read by
    the build itself);
  - the Steinway and the kits made from their libraries' recordings.

  Every file is checked against its sha256 before it is used. Files are kept in a cache shared by every
  project (`~/.cache/holo-music`, or `HOLO_MUSIC_CACHE`), with the downloads they were made from beside
  them. `--from DIR` points a build at a folder that already has a pack (a HO[LO] data folder's
  `packs`, say), checked all the same. Generated spaces need no files. Packs you imported yourself
  aren't pinned: a song that plays one says so when it's built.
- **Node.js is pinned too**, to the exact version that ran `holo init` (or `holo update-engine`): the
  build refuses another, so a rebuild is the same on any computer. Install that version (nvm, fnm,
  volta…), or pass `--any-node` to build with yours (the build records it).

`node music/holo/holo-music.mjs help` lists the rest: `render PIECE` (one song, anywhere), `fetch`,
`check`, `version` and `compare A.wav B.wav`.

### A song's own recordings

Send copies a song's audio files into `<piece>.audio/` beside it (and removes those it no longer plays);
bringing a piece into the studio brings them with it. They are committed with the project. For long
recordings the plan is Git LFS (`git lfs track "music/sessions/*.audio/**"`), or a store fetched by
checksum as the sample libraries are; neither is built yet.

### Engine versions

An experience stays on the engine it pinned until you move it. When the studio's engine is newer, the
experience's group in *Songs* says so: **Builds with engine 0.1.0+4ba9e85 · holo update-engine**
(hover it for the dates), so a difference between what you hear and what the project builds is never a
mystery. (The studio knows its own engine's commit from git, or, in Docker, from the stamp its image
carries: CI writes it before publishing the image, and `pnpm run up` before building one.)

"Newer" means newer in what the experience plays:
- the engine's code changed, or
- a pack its songs play has a new map.

A pack it doesn't play, new or changed, doesn't count. So a new pack arriving in the studio doesn't
badge every experience.

```bash
holo update-engine ../my-experience
```

pins this HO[LO]'s engine (as its last commit has it: work in progress never goes into a pin; `--ref`
pins another commit or tag) with the packs its songs play, rebuilds every song with it and says how far
each one moved. When the engine is the same and only the packs its songs play changed, it pins those
and builds what changed, nothing more:

```
How far each song moved:
  theme: identical, sample for sample
  boss: differs from 12.400 s by at most -96.1 dBFS, 118.0 dB under the song
```

Commit `holo.creation.json` and `music/holo/` together.
